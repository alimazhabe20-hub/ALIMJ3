# ALIMJ — Architecture & Editing Rules

## هدف اصلی
این پروژه عمداً به شکل **Facade + Parts** نگهداری می‌شود تا افزودن قابلیت جدید، تا حد ممکن بدون دستکاری فایل‌های اصلی انجام شود.

## قانون اجباری برای ویرایش‌های بعدی
1. **فایل‌های اصلی (`*.py` در سطح اصلی هر feature/service/handler) را بی‌دلیل ویرایش نکن.**
2. قبل از تغییر فایل اصلی، ابتدا پوشه‌ی هم‌نام `*_parts/` را بررسی کن.
3. قابلیت جدید را ترجیحاً در یک فایل جدید و کوچک داخل `*_parts/` اضافه کن.
4. اگر قابلیت موجود قابل توسعه است، همان part فرعی را ویرایش کن؛ فایل اصلی فقط باید نقش API/Facade/Orchestrator پایدار را داشته باشد.
5. هیچ قابلیت موجود، handler، callback، import، API، تنظیمات، رفتار runtime یا compatibility نباید صرفاً برای modularization حذف شود.
6. `requirements.txt` بدون درخواست صریح کاربر تغییر نکند.
7. نام و مسیر APIهای عمومی موجود حفظ شود؛ refactor نباید callerهای قدیمی را مجبور به تغییر کند.
8. فایل‌های `part_999_core_legacy.py` **منبع سازگاری legacy هستند و نباید محل توسعه قابلیت‌های جدید باشند**. برای قابلیت جدید part جدید بساز.
9. قبل از تحویل، حداقل `compileall` و تست‌های موجود پروژه اجرا شوند و هر خطای واقعی گزارش شود.
10. اگر تغییر واقعاً نیازمند تغییر Facade است، تغییر را حداقلی نگه دار و دلیل آن را در گزارش نهایی بنویس.

## الگوی مجاز
```text
bot/feature.py                 # Facade کوچک و پایدار
bot/feature_parts/
    part_001_existing.py
    part_002_new_capability.py # توسعه‌های آینده اینجا
    part_999_core_legacy.py    # legacy؛ دست‌نخورده مگر برای رفع باگ ضروری
```

## نتیجه مورد انتظار
در نسخه‌های بعدی، برای قابلیت‌های جدید اولویت با **فایل جدید یا part فرعی** است؛ نه بازنویسی فایل اصلی.
